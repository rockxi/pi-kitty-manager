# Технический проект: панель pi-агентов для kitty

**Статус:** исходный архитектурный проект; рабочий MVP реализован. Точное соответствие и ограничения описаны в [статусе реализации](implementation-status.md), запуск — в [инструкции установки](installation.md). Непомеченные предложения ниже не следует считать уже реализованными.

**Рабочее название:** Pi Kitty Agents (`pi-kitty`).
**Основная платформа:** macOS + kitty; архитектура с возможностью поддержки Linux.

## 1. Задача

Пользователь одновременно работает с несколькими pi-агентами в разных вкладках и панелях kitty. Нужен единый локальный реестр, который отвечает на вопросы:

- Какие агенты сейчас запущены?
- В каких проектах и сессиях они работают?
- Какие выполняют задачу, а какие свободны?
- В каком экземпляре kitty, системном окне, вкладке и панели находится каждый?
- Как быстро перейти к нужному агенту, не перебирая вкладки вручную?

Основной сценарий: **горячая клавиша → поиск/выбор агента → Enter → фокус на его терминале**.

Под «активным агентом» понимается запущенный экземпляр pi, в том числе ожидающий следующего запроса. Это не обязательно агент, который прямо сейчас генерирует ответ.

## 2. Объём первой версии

### Входит в MVP

- Один пользовательский даемон на локальной машине.
- Регистрация pi через расширение, heartbeat и восстановление соединения.
- Состояния выполнения и актуальные метаданные сессии.
- Обнаружение pi без расширения в известных экземплярах kitty с ограниченной достоверностью.
- Поддержка нескольких экземпляров kitty, системных окон, вкладок и split-панелей.
- Kitten со списком **только pi-агентов**, текстовым поиском и управлением с клавиатуры.
- **Группировка по рабочим папкам по умолчанию**; цветные статусы и настоящие названия текущих диалогов pi, не заголовки вкладок.
- Переход к конкретной панели, а не только к вкладке.
- Диагностика установки, соединений и разрешений.
- Автозапуск через macOS LaunchAgent.

### Не входит в MVP

- Веб-интерфейс, Electron-приложение, меню-бар.
- Отправка промптов, остановка и перезапуск агентов, управление заданиями.
- Чтение переписки, скриншоты терминала, сбор tool arguments/results.
- Каталог завершённых сессий, аналитика токенов и стоимости.
- Автоматическое переключение внутренних окон tmux/screen.
- Обнаружение агентов на удалённых машинах по SSH.
- Точное определение произвольных диалогов сторонних расширений pi.

## 3. Термины и идентичность

У kitty есть несколько уровней, которые нельзя смешивать:

```text
машина / пользователь
└── экземпляр процесса kitty
    └── системное окно (OS window)
        └── вкладка (tab)
            └── терминальная панель (kitty window)
                └── shell / процесс pi
                    └── текущая сессия pi
```

`KITTY_WINDOW_ID` — ID терминальной панели, не системного окна. ID вкладки не равен её видимому порядковому номеру. ID окон имеют смысл только внутри конкретного экземпляра kitty.

| Идентификатор | Назначение |
|---|---|
| `kitty_instance_id` | Сгенерированный даемоном ID проверенного процесса kitty; связан с PID, временем старта и endpoint |
| `agent_id` | Случайный UUID экземпляра процесса pi; сохраняется при `/reload` и смене сессии внутри процесса |
| `generation` | Новый UUID жизненного цикла расширения; меняется при reload/замене runtime |
| `session_id` | ID текущей сессии pi; может меняться без смены процесса |
| `pid` + `process_started_at` | Проверка жизнеспособности и защита от повторного использования PID |
| `window_id` | ID панели внутри экземпляра kitty |

`agent_id` нельзя заменять на `session_id`: одну сессию могут открыть два процесса. Для сохранения `agent_id` между reload расширение использует собственную process-local переменную окружения, связанную с `process.pid`. Дочерний pi обязан создать новый ID, если унаследованный PID не совпадает с его собственным.

## 4. Архитектура

```text
┌──────────────────────────┐        ┌──────────────────────────┐
│ pi + extension.ts        │        │ pi + extension.ts        │
│ lifecycle + heartbeat    │        │ lifecycle + heartbeat    │
└─────────────┬────────────┘        └─────────────┬────────────┘
              └─────────────────┬────────────────┘
                         Unix domain socket
                                │
                     ┌──────────▼───────────┐
                     │ pi-kitty daemon      │
                     │ registry + discovery │
                     │ kitty topology       │
                     │ focus coordinator    │
                     └───────┬───────▲──────┘
                             │       │ list / subscribe / focus
                Kitty Remote │       │
                     Control │  ┌────┴─────────────────┐
                             │  │ kitten: agents.py    │
                     ┌───────▼┐ │ overlay + поиск      │
                     │ kitty  │ └──────────────────────┘
                     └────────┘
```

### 4.1. Даемон

Долгоживущий пользовательский процесс:

- принимает регистрации и снимки состояния;
- хранит реестр агентов и известных экземпляров kitty;
- получает дерево окон через `kitty @ --to <endpoint> ls`;
- уточняет расположение при переносе панели между вкладками/системными окнами;
- обнаруживает процессы pi без расширения;
- проверяет heartbeat и завершение процессов;
- публикует изменения списка;
- исполняет ограниченную операцию `focus`.

Один успешный опрос `ls` на экземпляр kitty обслуживает всех его агентов. Не запускаем отдельный опрос для каждого агента.

Реестр в памяти — источник актуального состояния. После перезапуска он восстанавливается по повторной регистрации расширений и discovery. Сохранённые записи не считаются живыми без проверки.

### 4.2. Расширение pi

Небольшой TypeScript-модуль внутри pi. Не меняет промпты и не добавляет модельные инструменты.

Задачи:

- получить PID, cwd, session ID/name, модель, режим pi;
- передать `KITTY_PID`, `KITTY_WINDOW_ID`, `KITTY_LISTEN_ON`, если доступны;
- отправлять полный снимок при подключении и изменениях;
- раз в 5 секунд отправлять heartbeat с полным актуальным снимком;
- при недоступности даемона продолжать работу pi без ошибок и блокировок.

Длительные ресурсы создаются в `session_start`, а не в фабрике расширения. `session_shutdown` закрывает ресурсы идемпотентно. Он вызывается не только при выходе процесса, но и при смене сессии/reload, поэтому означает завершение поколения регистрации, а не обязательно смерть агента.

Метаданные сессии берутся из `ctx.sessionManager`, а не из унаследованных `PI_SESSION_*`: окружение может не отражать последующую смену сессии.

### 4.3. Kitten

Пользовательское расширение kitty на Python:

- запускается по сочетанию клавиш поверх текущей панели;
- получает snapshot и подписывается на изменения;
- рисует список и строку поиска;
- возвращает выбранный `agent_id`, но не самостоятельно выбранные пользователем shell-команды;
- закрывается без воздействия на терминал при Escape.

UI-процесс не является вторым даемоном и не хранит собственный реестр. Для TUI используем инфраструктуру kittens, доступную в согласованной версии kitty; конкретный минимальный набор API закрепляется после прототипа совместимости.

### 4.4. CLI

Предлагаемые команды:

```text
pi-kitty daemon run
pi-kitty list [--json]
pi-kitty focus <agent-id>
pi-kitty doctor
pi-kitty service install
pi-kitty service uninstall
```

Сервисные команды устанавливают/удаляют только собственный LaunchAgent. Изменения kitty/pi конфигурации выполняются явно с подтверждением или выдаются как инструкция.

## 5. Источники данных и достоверность

### 5.1. Приоритет источников

1. **Расширение pi:** точный процесс, текущая сессия, состояние агента.
2. **Kitty `ls`:** фактическая топология, заголовки, foreground processes, фокус.
3. **Информация ОС о процессах:** время старта, родительские связи, проверка завершения.

Заголовки вкладок и терминала используются только как подписи. По ним нельзя устанавливать личность агента или выбирать цель переключения.

### 5.2. Агенты без расширения

В `ls` доступны `foreground_processes`, PID и command line. Даемон распознаёт прямые запуски pi по исполняемому файлу/известному entry point, при необходимости проверяя родительскую цепочку. Сопоставление по одному вхождению строки `pi` недопустимо.

Без расширения запись содержит процесс, cwd и расположение; `activity = unknown`, `session_id = null`, `source = process`. Неоднозначные совпадения показываются как кандидаты, а не как подтверждённые агенты. Обёртки, переименованные бинарники и глубокие фоновые процессы могут не обнаружиться — универсальная полнота для такого режима не обещается.

После подключения расширения discovery-запись объединяется с подтверждённой по PID и времени старта; дубликат не создаётся. Предварительный `agent_id` discovery-записи может смениться, клиент получает удаление старой и добавление новой записи.

### 5.3. Обнаружение экземпляров kitty

Источники endpoint:

- регистрация расширения pi;
- окружение kitten при открытии списка, даже если в этом экземпляре пока нет pi;
- явный список endpoint в настройках;
- сканирование только собственного настроенного runtime-каталога сокетов kitty.

По умолчанию не сканируем все сокеты `/tmp` и не читаем окружение всех пользовательских процессов. Экземпляр kitty без доступного endpoint и без регистрации неизвестен даемону; это диагностируемое ограничение, а не «агентов нет».

### 5.4. Привязка к панели

1. Проверить локальный Unix endpoint и личность процесса kitty.
2. Получить дерево `ls`.
3. Найти заявленный `window_id` в этом экземпляре.
4. По возможности подтвердить процесс pi через foreground PID или родительскую цепочку.
5. Сохранить актуальные tab/OS window ID и подписи.

Переменные окружения — подсказка, не безусловное доказательство: они наследуются дочерними и удалёнными процессами. При неоднозначности запись остаётся видимой, но переключение блокируется с объяснением.

Pi вне kitty можно зарегистрировать с `location = null`; он отображается в отдельной группе «Вне kitty» и недоступен для перехода. Для `rpc`/`json`/`print` режима показываем режим; привязку к терминалу не обещаем. В списке по умолчанию — интерактивные агенты и обнаруженные локальные процессы pi.

## 6. Модель состояния

Состояние разделено на независимые измерения:

| Поле | Значения | Смысл |
|---|---|---|
| `presence` | `online`, `stale`, `offline` | Свежесть регистрации и жизнеспособность процесса |
| `activity` | `idle`, `busy`, `unknown` | Выполняет ли pi автоматическую работу |
| `phase` | `starting`, `model`, `tools`, `unknown` | Дополнительная фаза; необязательная подсказка |
| `location_status` | `verified`, `unverified`, `unreachable`, `outside_kitty` | Можно ли безопасно перейти |
| `last_outcome` | `success`, `error`, `aborted`, `unknown` | Результат последнего запуска, если доступен |

Ошибка последней задачи не означает смерть процесса. Недоступный kitty не означает, что pi завершился. Отсутствие stream-событий не означает `idle`.

### 6.1. События pi

| Событие | Реакция |
|---|---|
| `session_start` | Новое поколение, соединение, полная регистрация; начальное состояние через `ctx.isIdle()` |
| `before_agent_start` / `agent_start` | `busy`, сброс прошлого outcome |
| `turn_start` | Подсказка фазы `model` |
| `tool_execution_start/end` | Множество активных tool call ID; `tools`, пока оно непустое |
| `agent_end` | Не переводить в `idle`: возможны retry и продолжения |
| `agent_settled` | Обновить состояние после окончания автоматических продолжений |
| `model_select` | Обновить модель |
| `session_shutdown` | Best-effort unregister данного поколения, закрыть соединение и таймеры |

Heartbeat повторно читает безопасно доступные метаданные и `ctx.isIdle()`, чтобы исправлять пропущенные переходы. `phase` — best-effort, не строгая телеметрия внутренних запросов. Параллельные tools учитываются множеством ID, а не одним флагом. События вложенных tools не должны преждевременно завершать фазу.

Для outcome адаптер использует только подтверждённые поля событий/финального сообщения; если достоверного результата нет, оставляет `unknown`. Не определяем ошибки по тексту ответа.

Состояние «ждёт подтверждения» не выводим из отсутствия активности: у произвольных UI-диалогов расширений нет универсального наблюдаемого события. Это возможное будущее расширение протокола.

### 6.2. Heartbeat и очистка

Предлагаемые значения:

- heartbeat: 5 секунд;
- `stale`: после 15 секунд без обновления;
- скрытие из основного списка: после 60 секунд без обновления;
- окончательное удаление временной stale-записи: через 5 минут;
- подтверждённое завершение процесса: немедленно убрать из активных;
- после пробуждения macOS: перепроверить процессы и дать 15 секунд на переподключение.

Истечение TTL означает потерю наблюдения, а не доказанное завершение. Живой процесс с потерянной регистрацией может остаться discovery-записью с `activity = unknown`.

Для локальных интервалов используется монотонное время. Wall-clock timestamps нужны только для отображения/логов.

## 8. Локальный протокол

### 8.1. Транспорт

Unix domain stream socket, UTF-8 NDJSON: одно JSON-сообщение на строку. Это собственный протокол, не JSON-RPC pi.

- `v: 1` — версия протокола.
- `id` — ID запроса; ответ повторяет его.
- `method` — операция; `params` — аргументы.
- Ответ: либо `result`, либо `error` с машинным `code` и пользовательским `message`.
- Максимум строки: 64 KiB; общий snapshot при большом списке передаётся ограниченными частями.
- Deadline обычного запроса: 2 секунды; focus: 5 секунд.
- Неизвестная версия отклоняется явно; неизвестные необязательные поля игнорируются.

Пример:

```json
{"v":1,"id":"q1","method":"agents.list","params":{"include_stale":false}}
{"v":1,"id":"q1","result":{"revision":42,"agents":[]}}
```

### 8.2. Методы

| Метод | Кто вызывает | Назначение |
|---|---|---|
| `hello` | Любой клиент | Версия, роль, возможности, ID запуска даемона |
| `agent.register` | Расширение | Полный snapshot и новое соединение поколения |
| `agent.update` | Расширение | Полный snapshot + generation + возрастающий seq |
| `agent.heartbeat` | Расширение | Полный snapshot для самовосстановления |
| `agent.unregister` | Расширение | Отозвать только своё поколение |
| `kitty.announce` | Kitten/CLI | Предложить локальный endpoint для проверки |
| `agents.list` | Kitten/CLI | Snapshot реестра |
| `agents.subscribe` | Kitten | Первичный snapshot, затем изменения с revision |
| `agents.focus` | Kitten/CLI | Перейти к проверенной записи по `agent_id` |
| `health` | CLI | Состояние и предупреждения диагностики |

Подписка отправляет начальный snapshot и дальнейшие revisions в одном упорядоченном потоке, без гонки между отдельными list и subscribe. После разрыва — новая подписка с полным snapshot. Медленный подписчик отключается при превышении ограниченной очереди, не тормозя реестр.

### 8.3. Поколения, порядок, переподключение

Daemon хранит текущую generation и seq для каждого агента. Update/unregister старого поколения не меняет новое. В одном поколении меньший или повторный seq игнорируется.

Новое соединение от того же процесса получает новый lease; предыдущий lease отзывается. Новый runtime не принимает запоздалые ответы старого. При смене сессии UI может увидеть короткий переходный разрыв, но не постоянный дубликат.

Расширение хранит только последнее состояние, а не бесконечную очередь событий. Сетевые обработчики не блокируют stream pi. При переподключении отправляется полный snapshot.

Reconnect: 0.5 → 1 → 2 → 5 → максимум 10 секунд с jitter. Heartbeat/timers не удерживают завершающийся процесс pi. На unregister действует короткий deadline; недоступный даемон не задерживает выход.

Коды ошибок: `INCOMPATIBLE_PROTOCOL`, `INVALID_REQUEST`, `AGENT_NOT_FOUND`, `AGENT_STALE`, `LOCATION_UNVERIFIED`, `KITTY_UNREACHABLE`, `FOCUS_FAILED`, `PERMISSION_DENIED`.

## 9. Синхронизация с kitty и переключение

### 9.1. Топология

- Опрос известных экземпляров: раз в 2 секунды.
- При открытом списке: раз в 1 секунду, общий опрос, а не по подписчику.
- Ошибки одного экземпляра изолированы; backoff до 30 секунд.
- При Enter — внеочередная проверка цели, даже если кэш ещё свежий.
- Процессы `kitty @` ограничены timeout и размером stdout; парсится только необходимая часть результата.
- Полные `env` из `ls` не хранятся и не логируются.

Перенос панели между вкладками одного экземпляра обновляет расположение при следующем опросе. Перенос между независимыми процессами kitty не считается автоматически поддерживаемым переносом живой панели.

### 9.2. Алгоритм focus

1. Получить запись по `agent_id`; проверить presence и актуальность процесса.
2. Перечитать `ls` конкретного экземпляра.
3. Проверить, что panel ID ещё существует и связан с нужным процессом, а не просто с прежним заголовком.
4. Дождаться закрытия overlay, если запрос пришёл из kitten.
5. Выполнить `focus-window --match id:<window_id>` с явным `--to` и проверкой ответа.
6. Проверить, что целевая панель стала активной; при необходимости использовать подтверждённый для поддерживаемой версии дополнительный шаг выбора вкладки/поднятия системного окна.
7. Обновить MRU только после успешного переключения.

Не используем `--no-response`: иначе отсутствие цели можно ошибочно принять за успех. Не выбираем цель по tab index или title. Смена вкладки обычно является следствием `focus-window`, но поведение поднятия системного окна и смены Space на macOS нужно проверить интеграционным тестом, а не обещать по названию команды.

Даемон запускает команды через argv, без shell. Клиент не может передавать произвольную remote-control команду.

### 9.3. Жизненный цикл overlay

Важная гонка: если переключиться до закрытия kitten, закрытие overlay может вернуть фокус в исходное окно.

Предлагаемый порядок:

- `main()` возвращает выбранный agent ID и контекст overlay;
- `handle_result()` только запускает короткоживущий CLI-клиент, не выполняет блокирующее ожидание внутри GUI-процесса kitty;
- CLI передаёт `agents.focus` с ID исходного overlay и экземпляра;
- даемон ожидает исчезновения именно этого overlay в `ls`, затем переводит фокус;
- ожидание ограничено deadline, а не фиксированным `sleep`;
- повторный Enter подавляется уникальным request ID.

Точная доступность overlay ID и порядок callback проверяются первым прототипом на целевой версии kitty. Если механизм не подтверждается, реализация блокируется до выбора проверенного варианта post-close dispatch; случайная задержка не является решением.

Ошибки после закрытия списка записываются в диагностику и кратко показываются через поддерживаемый механизм уведомления kitty; если его нет — сохраняются для следующего открытия списка и CLI. Нельзя молча утверждать успешный переход.

## 10. Интерфейс kitten

Предлагаемая горячая клавиша: `ctrl+shift+p`. Она действует в kitty, не является глобальной системной комбинацией и должна быть переназначаемой. Перед установкой проверяем конфликт с существующей привязкой.

```text
Pi agents · 3 online · 1 busy                  [связь: OK]
> _

~/projects/backend
› Работает     Рефакторинг API      окно 1 / вкладка 2 / панель 5
  Неизвестно   Без расширения pi    окно 2 / вкладка 1 / панель 2
~/projects/frontend
  Свободен     Проверка формы       окно 1 / вкладка 3 / панель 7

↑↓ выбрать   Enter перейти   Esc закрыть   Ctrl+R обновить
```

### Поведение

- Один агент — одна строка; две pi-сессии в одной панели не объединяются.
- Поиск по проекту/cwd, session name, модели, заголовку вкладки.
- Сначала substring/token matching без внешней зависимости; fuzzy matching можно добавить позже.
- Сортировка по недавнему успешному переходу через панель; текущий агент отмечается отдельно. Это MRU панели, не полная история фокуса ОС.
- При обновлениях выбор сохраняется по `agent_id`, а не по номеру строки.
- Автоматическая пересортировка во время ввода отключена, чтобы цель не «уезжала» из-под Enter.
- Потеря соединения оставляет последний список с явной пометкой и запрещает переход без перепроверки.
- В узком окне скрываются второстепенные колонки; подробности выбранной строки — ниже списка.
- Unicode обрезается по терминальным колонкам; ANSI/OSC в метаданных не исполняются.
- Статус обозначается текстом, не только цветом. Иконки/Nerd Fonts не обязательны.
- Escape не отправляет символы в pi и не меняет исходный фокус.

Отдельные состояния: «агентов нет», «нет доступных экземпляров kitty», «даемон недоступен», «не хватает разрешений», «найдены только неподтверждённые агенты». Эти ситуации нельзя сводить к пустому списку.

## 12. Конфигурация и установка

### 12.1. Пути

- Конфигурация: `${XDG_CONFIG_HOME:-~/.config}/pi-kitty/config.toml`.
- Runtime: `$XDG_RUNTIME_DIR/pi-kitty`, если каталог существует, принадлежит пользователю и безопасен.
- На macOS без XDG runtime: `~/Library/Caches/pi-kitty/run`.
- На Linux без XDG runtime: приватный каталог в пользовательском cache с проверкой владельца.
- Сокет: `<runtime>/daemon.sock`.
- Логи macOS: `~/Library/Logs/pi-kitty/` с ротацией и ограничением размера.

Одинаковый алгоритм пути реализуется во всех клиентах. Для слишком длинного пути Unix socket выдаётся понятная ошибка и поддерживается явное переопределение. Нельзя полагаться на cwd, PATH интерактивного shell или наследование переменных от LaunchAgent.

Пример будущей конфигурации:

```toml
[daemon]
heartbeat_seconds = 5
stale_after_seconds = 15
hide_after_seconds = 60

[kitty]
command = "/opt/homebrew/bin/kitty"
poll_seconds = 2
# Дополнительные endpoint; обычно приходят от расширения или kitten.
endpoints = []

[ui]
sort = "mru"
show_stale = false
```

### 12.2. Kitty

Базовый профиль интеграции:

```conf
allow_remote_control socket-only
listen_on unix:${HOME}/Library/Caches/pi-kitty/run/kitty-{kitty_pid}.sock
map ctrl+shift+p kitten /absolute/path/to/pi-kitty/kitty/agents.py
```

Каталог создаётся установщиком до запуска kitty с mode `0700`. На Linux путь другой. Значение endpoint читается из фактического `KITTY_LISTEN_ON`: нельзя самостоятельно добавлять PID второй раз. В kitty без `{kitty_pid}` PID может добавляться к имени автоматически.

`socket-only` разрешает **все** remote-control команды любому процессу с доступом к сокету. Это не ограниченный режим «только focus». Он исключает управление через TTY, но не изолирует процессы того же пользователя. Установка должна явно объяснять этот компромисс.

Более строгий профиль с password/policy и allowlist только `ls`, `focus-window` и, если нужен, `focus-tab` рассматривается отдельно после проверки сочетания socket/password на целевой версии. Нельзя обещать allowlist поверх `socket-only`, который принимает socket-запросы безусловно.

Изменение `listen_on` требует перезапуска kitty; простого reload конфигурации недостаточно. Установщик не завершает существующие окна автоматически.

### 12.3. Pi

Расширение устанавливается как пользовательский pi package либо в пользовательский каталог расширений. Предпочтителен отдельный пакет с явным manifest:

```json
{
  "name": "pi-kitty-agent-extension",
  "keywords": ["pi-package"],
  "pi": {"extensions": ["./index.ts"]},
  "peerDependencies": {"@earendil-works/pi-coding-agent": "*"}
}
```

Host-пакет pi не включается в runtime dependencies расширения. Пакет устанавливается персонально, чтобы отслеживать pi независимо от project trust и текущего репозитория.

Уже запущенным pi потребуется загрузка расширения через `/reload` после установки либо перезапуск. До этого они могут отображаться только через discovery. Запуски с отключёнными расширениями остаются ограниченным режимом.

### 12.4. Автозапуск

LaunchAgent запускает daemon в foreground, использует абсолютные пути к Python/entry point и log-файлам, `KeepAlive` и ограничение частоты рестартов. Даемон не делает double-fork.

Перед bind проверяются singleton lock и существующий сокет. Чужой или живой сокет не удаляется. Stale socket удаляется только после проверки владельца и отсутствия работающего сервера.

В первоначальном проекте предполагался только LaunchAgent. По уточнённому требованию MVP поддерживает **автозапуск непосредственно при старте kitty**: глобальный watcher `on_load` запускает внешний worker с идемпотентным `daemon ensure`. GUI не блокируется; singleton lock предотвращает дубли при одновременном старте нескольких экземпляров. Pi/kitten сами не порождают daemon при каждом запросе. LaunchAgent остаётся необязательной альтернативой.

## 13. Безопасность и приватность

- Нет TCP listener, root и сетевого доступа для работы панели.
- Runtime-каталог `0700`, сокет `0600`, проверка владельца и peer UID там, где ОС предоставляет API.
- Доверительная граница — пользователь ОС. Процессы с тем же UID не считаются надёжно изолированными; поле `role` протокола само по себе не авторизация.
- Принимаются только локальные Unix endpoint, принадлежащие пользователю, из согласованных каталогов/явной конфигурации.
- Endpoint из окружения проходит проверку; daemon не подключается к произвольному TCP адресу.
- Для каждого endpoint: timeout, ограничение stdout и числа параллельных subprocess.
- Нет произвольного shell execution и proxy произвольных kitty-команд.
- Не собираем промпты, ответы, tool arguments/results, auth.json, API keys и полный env процессов.
- Cwd и session name могут быть чувствительными: показываются локально, не попадают в обычные логи без необходимости.
- Внешние заголовки и строки очищаются от control chars/ANSI/OSC; ограничения длины применяются до рендера.
- Debug-логи включаются явно, имеют ротацию и не записывают исходный `ls` целиком.

## 14. Отказы и пограничные случаи

| Ситуация | Ожидаемое поведение |
|---|---|
| Daemon перезапущен | Расширения переподключаются и восстанавливают snapshot |
| Pi убит SIGKILL | Проверка процесса или TTL убирает активную запись |
| `/new`, `/resume`, `/reload` | Новое поколение; нет постоянных дубликатов; session ID обновляется |
| Панель перенесена в другую вкладку | Расположение обновляется, Enter перепроверяет дерево |
| Панель закрыта после выбора | `AGENT_NOT_FOUND`/`FOCUS_FAILED`, никакого перехода в чужую панель |
| Один kitty недоступен | Остальные продолжают работать, проблемный помечен |
| Один session ID у двух процессов | Две строки по разным `agent_id` |
| Несколько pi в одной панели | Несколько строк; переход только к панели, не к конкретному foreground job |
| Sleep/wake macOS | Grace period, повторный опрос, без ложного массового «завершения» |
| SSH/tmux унаследовали KITTY_* | Не считать привязку доказанной; ограниченный/неподдерживаемый переход |
| Сокет или протокол несовместимы | Диагностика версии и пути, pi продолжает работать |
| Нет прав Remote Control | Явное предупреждение, а не пустой список |
| Pi без extension | Discovery с `unknown`, без выдуманных статусов |

## 15. Производительность и наблюдаемость

Целевой бюджет первой версии: 100 агентов и 10 экземпляров kitty на одной машине.

- Первичный snapshot из работающего daemon: p95 < 100 мс.
- Открытие kitten с кэшированным списком: целевой p95 < 300 мс на целевой машине.
- Отражение lifecycle-события: обычно < 1 секунды.
- Отражение переноса панели: не дольше интервала опроса + времени `ls`.
- Переход: целевой p95 < 500 мс без смены macOS Space; deadline 5 секунд.
- Idle CPU daemon: целевой средний < 1% одного ядра; подтвердить замерами.
- Очереди, история MRU, входные сообщения и логи ограничены.

Это критерии измерения, не гарантии до прототипа. Время запуска Python/kitty и поведение macOS замеряются отдельно.

`pi-kitty doctor` проверяет: версии pi/kitty, наличие сервиса, владельца сокета, handshake, актуальность heartbeats, известные endpoint, результат `ls`, поддержку focus, загрузку расширения и необходимость перезапуска kitty. Не делает пробное переключение без явного согласия.

## 16. Тестирование

### Unit

- Протокол: фрагментированные строки, несколько сообщений в read, невалидный JSON, слишком большие сообщения.
- Реестр: seq/generation, unregister старого runtime, TTL, повторное использование PID.
- Состояния: продолжения после `agent_end`, параллельные и вложенные tools, reconnect snapshot.
- Топология: несколько kitty с совпадающими window ID, переносы, исчезновения.
- Discovery: прямой pi, node entry point, shell wrapper, ложные совпадения, dedup.
- UI: фильтр, стабильность выбора, маленький терминал, Unicode и управляющие последовательности.
- Безопасность: чужой UID/socket, недоверенный endpoint, shell injection, медленный подписчик.

### Integration

- Fake kitty executable с fixtures JSON и управляемыми ошибками/timeout.
- Настоящие Unix socket клиенты и перезапуск daemon.
- Протокольные contract tests Python ↔ TypeScript с общими fixtures.
- Настоящее расширение pi: старт, `/reload`, новая сессия, смена модели, выход.
- Настоящий kitty: overlay закрывается до focus, callback не блокирует GUI.
- macOS: два системных окна, разные Spaces, свёрнутое окно; фиксируем реальные ограничения ОС.

### Приёмочный сценарий

1. Запустить daemon и два экземпляра kitty с Remote Control.
2. Открыть минимум три pi в разных вкладках и split-панелях.
3. Убедиться, что список содержит каждую запись ровно один раз и верное расположение.
4. Запустить задачу в одном pi: `busy`, после полного завершения — `idle`.
5. Горячей клавишей перейти в другую вкладку и другое системное окно, включая второй экземпляр kitty.
6. Отменить список: исходный терминал и ввод остаются без изменений.
7. Перенести панель: список обновляет вкладку, Enter находит прежнего агента.
8. Выполнить `/reload` и сменить сессию: дубликатов нет, метаданные актуальны.
9. Убить pi и перезапустить daemon: призрачных online-записей нет, остальные восстанавливаются.
10. Запустить pi без расширения: видна ограниченная discovery-запись, без ложного `idle`.

## 17. План реализации

### Этап 0. Проверка интеграций — обязательный gate

Минимальный прототип вне production-кода:

- проверка безопасного runtime-каталога и Remote Control конфигурации.

**Результат:** таблица проверенных версий и подтверждённый механизм focus. До этого не фиксируем обещания по внутренним kitty API и минимальной версии.

### Этап 1. Daemon и протокол

Socket server, singleton, реестр, health/list, kitty adapter, fixtures, unit tests.

### Этап 2. Расширение pi

Lifecycle, snapshot, heartbeat, reconnect, поколения, contract tests. Проверка отсутствия влияния на скорость и завершение pi.

## 18. Проверенные факты и открытые решения

### Проверено при подготовке проекта

- Установлен kitty `0.45.0`; команды `ls`, `focus-window`, `focus-tab` доступны.
- Текущий экземпляр предоставляет `KITTY_PID`, `KITTY_WINDOW_ID`, `KITTY_LISTEN_ON`.
- Read-only запрос `ls` через текущий Unix endpoint сработал; обнаружены два foreground-процесса pi в разных вкладках.
- В установленном pi API есть session lifecycle, `agent_settled`, `ctx.isIdle()`, session manager и `model_select`.
- Документация pi запрещает создавать долгоживущие ресурсы в фабрике и требует очистку на `session_shutdown`.
- Официальная документация kitty описывает custom kitten overlay и предупреждает о нестабильности прямых внутренних API.
- `socket-only` принимает socket-команды безусловно; изменение `listen_on` через reload не поддерживается.

Никакие операции переключения, установка сервиса или изменения пользовательской конфигурации при подготовке документа не выполнялись.

### Предлагаемые defaults для согласования

1. macOS — первая платформа, Linux после MVP.
2. `ctrl+shift+p` — сочетание по умолчанию, при конфликте выбирается другое.
3. Первая версия наблюдает и переключает, но не отправляет команды агентам.
4. «Все агенты» в строгом режиме — процессы с установленным расширением; discovery расширяет покрытие, но не гарантирует полноту.
5. SSH и внутренние tmux-панели — вне первой версии.
6. Стартовый Remote Control профиль — локальный Unix socket с явно описанным уровнем доверия.
